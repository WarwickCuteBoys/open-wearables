## Overview

Google Health data reaches Open Wearables through two independent paths that share the single `google` provider identity:

- **Health Connect (mobile SDK)** — data pushed from an Android device via the Mobile SDK. See the [Android SDK guide](/sdk/android/integration).
- **Google Health API (cloud OAuth)** — this guide. A server-side OAuth 2.0 flow against the [Google Health API](https://developers.google.com/health) that lets you connect a user's Google account and pull their data over REST, plus receive notify-only webhooks.

The Google Health API is an **aggregation layer**: it surfaces data from *every* source connected to the user's Google Health account — the phone's Health Connect store, Fitbit, Google Fit, and other apps — not just one device.

### Supported data types

| Data type | Path |
|-----------|------|
| Steps, distance, calories, hydration | 24/7 metrics |
| Heart rate, resting heart rate, HRV (RMSSD + SDNN) | 24/7 metrics |
| VO₂ max, respiratory rate, SpO₂ | 24/7 metrics |
| Weight, body fat, core body temperature, blood glucose | 24/7 metrics |
| Workouts (Exercise sessions) | Sessions |
| Sleep (with stages) | Sessions |

### Data delivery

| Method | Description |
|--------|-------------|
| **Polling (pull)** | Open Wearables periodically fetches data via the Health API (Celery Beat), driven by the [fetch mode](#data-granularity-and-fetch-modes) below. |
| **Webhooks (notify-only)** | Google sends a lightweight ping naming the changed `dataType` and time intervals; Open Wearables then fetches the changed data over REST. Requires a project-level [subscriber registration](#webhook-subscriber-registration). |

### Progressive historical sync

The 24/7 sync fetches total and active energy first, newest windows first, and
commits each metric window independently. Other time-series requests are also
bounded to one day, rather than buffering an entire multi-day raw backfill.
Successful windows survive a later failure and emit data-ready webhooks as soon
as the outer transaction commits. Notifications retain neither committed sample
arrays for the session lifetime nor data from rolled-back savepoints.

After energy, sleep from the last seven days is imported before older sleep and
raw activity, heart, body, and vital metrics. Recent sleep remains queryable
without waiting for the raw-metric backfill.

Sleep windows are adjacent and start-inclusive/end-exclusive. A session starting
at the split belongs only to the recent window; a session crossing it belongs to
the older window and is imported whole. Requests of seven days or less use one
sleep window; empty ranges do no work and reversed ranges are rejected. The
seven-day window is relative to the requested end, including historical-only
requests, not to the worker's current clock.

Each successful sleep window is committed before proceeding. The existing sleep
merge service also commits individual sessions, so a later error cannot undo
those sessions. A failed sleep window rolls back its pending transaction and
does not prevent other windows or metrics from being attempted. After successful
writes are committed, any fetch or write failures are logged and raised to the
sync task, which marks the 24/7 sub-task unsuccessful rather than reporting the
entire import as successful. The overall sync status still follows the existing
task's failure/partial-success rules.

Google pull ownership uses a 90-second lease renewed every 30 seconds. The worker
also verifies ownership before fetching another metric page and before database
flushes/commits. Detected ownership loss rejects subsequent writes rather than
continuing behind a replacement. Other providers retain their existing longer lock policy.
A killed Google worker therefore cannot leave a new four-hour blocking lock.
Legacy locks created by older versions retain their original expiry; do not
delete an unknown owner's lock during an upgrade.

Subscribe to `calories.created` for both `active_energy` and `total_energy`, or
their granular `series.active_energy.created` and `series.total_energy.created`
events. Energy corrections use content-sensitive idempotency keys: unchanged
retries deduplicate, but a revised value or interval is delivered again.
An enabled outgoing webhook destination and its matching signing key are still
required. Running Svix alone does not configure delivery to a consuming app.

### Trackable reconnect and historical requests

`POST /api/v1/google/users/{user_id}/sync/historical?days=8` keeps its existing
response fields and adds `run_id`, `requested_at`, and `coalesced` for Google:

```json
{
  "success": true,
  "provider": "google",
  "user_id": "11111111-2222-4333-8444-555555555555",
  "method": "pull_api",
  "task_id": "22222222-3333-4444-8555-666666666666",
  "run_id": "pull_0123456789abcdef0123456789abcdef",
  "requested_at": "2026-09-11T08:00:24.123456+00:00",
  "coalesced": false,
  "days": 8,
  "start_date": "2026-09-03T08:00:00+00:00",
  "end_date": "2026-09-11T08:00:00+00:00",
  "message": "Historical sync queued."
}
```

Requests use a UTC minute-aligned snapshot, excluding the incomplete current
minute. Redis atomically coalesces a request only when the same gateway user's
pending Google run contains its entire requested interval. A wider interval
gets a new job; a narrower request reuses the original run, task, days, and date
range. No second worker is enqueued for a coalesced request. Automatic
Google history on OAuth connect uses the same admission path. Reauthorization
preserves an existing Google live cursor; historical pulls never advance it.
Other providers retain their existing enqueue behavior.

Read `GET /api/v1/users/{user_id}/sync/runs` and match **both `run_id` and
`provider`**, not the latest historical run. `SyncRunSummary.metadata` now
includes the requested date range, `is_historical`, `task_id`, and tracking
information. When another Google owner holds the lease, retries keep the same
run and task IDs, dates, and source:

```json
{
  "stage": "queued",
  "status": "in_progress",
  "metadata": {
    "waiting_for_lock": true,
    "retry_after_seconds": 60,
    "is_historical": true,
    "request_tracking": true
  }
}
```

The actual summary also contains its normal run/provider/source/timestamp fields.
Retry delays are 60, 120, 240, 480, and 900 seconds. Scheduling failures and
exhaustion are terminal failures, not successful imports. A failed terminal run
allows a new explicit request immediately. Celery `SUCCESS` only means the
function returned; it says nothing about provider delivery.

Admission and the initial run record are atomic in Redis. Undelivered jobs expire
after five minutes, waiting retries after their countdown plus five minutes,
and running request admission after two minutes without a renewable ownership
heartbeat. Expired deliveries cannot resurrect their request. The read-only run
summary reports `failed` with `metadata.request_liveness_expired=true` when
admission has expired or disappeared without a terminal event. This diagnostic
does not fabricate a signed completion event or cancel a worker. An explicit
retry can safely create a new run; the provider lease still fences writes.
Redis coordination errors fail closed rather than dispatching untracked work.

`requested_at` is the original admission timestamp, also exposed in
`SyncRunSummary.metadata`. It does not change on coalescing, retries, progress,
or completion. To prefer requested historical work over unrelated live pulls,
filter for `provider=google`, `source=backfill`, and `metadata.is_historical=true`,
then select by `metadata.requested_at`, not `last_update` (which changes during
retries). Preserve the returned `run_id` when the historical POST supplies one.
Existing runs from before this addition may not have `requested_at`; missing
request metadata is not evidence that data was imported.

An importing application should mark data imported only after the corresponding
signed `sync.completed` event for that exact run has been imported, according to
its own success/partial-result policy. Neither a queued response, waiting retry,
OAuth success nor a Celery result proves import completion.
The outgoing envelope is `{"type":"sync.completed","data":{...}}`: the exact
admitted ID is `data.run_id`, with `data.provider`, `data.source`, `data.status`,
and `data.metadata`. Partial completion remains `data.status="partial"` and
summary `status="partial"`; it is never promoted to success. The Svix
idempotency key is `sync.completed.<run_id>`.

### Read-only Google lease inspection and stopped-owner recovery

Run the operator CLI from `backend/` inside an authorized gateway ECS container:

```bash
python -m scripts.google_sync_lock --user-id 11111111-2222-4333-8444-555555555555
```

It resolves the active Google provider account internally using the gateway UUID.
Output is concise JSON: `ttl_seconds`, SHA256 `owner_fingerprint`, token-bound
run/task/process/container/ECS metadata, and `ownership_verifiable`. It never
prints OAuth credentials, the provider account identifier, or the raw owner
token. Ordinary inspection only reads Redis, the database, ECS local task
metadata, and `ecs:DescribeTasks`.

Outside ECS, all four explicit environment checks are required:

```bash
python -m scripts.google_sync_lock \
  --user-id 11111111-2222-4333-8444-555555555555 \
  --cluster-arn arn:aws:ecs:ap-southeast-1:123456789012:cluster/gateway-test \
  --current-task-arn arn:aws:ecs:ap-southeast-1:123456789012:task/gateway-test/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa \
  --expected-redis-host redis.gateway.internal \
  --expected-database-host postgres.gateway.internal
```

Both storage hosts must match the configured gateway, and the inspecting ECS task
must be `RUNNING` in the exact region/account/cluster. Inside ECS, explicit ARNs
must also match the local container metadata. Operators are responsible for
selecting the authorized gateway environment and UUID; possession of a UUID is
not authentication.

Recovery is never automatic. Repeat inspection with `--recover` and
`--expected-fingerprint` set to the full 64-character fingerprint just inspected.
The CLI must establish token-bound owner evidence, verify the exact owning task
is `STOPPED` in the same cluster via read-only `DescribeTasks`, and atomically
compare-delete the observed Redis owner and its unchanged evidence. A changed
owner, expired/missing evidence, missing ECS task, denied AWS lookup, or live task
refuses recovery. The user's inactive connection and elapsed time are never proof
of abandoned ownership. Legacy locks have no ownership evidence and require
natural expiry; they cannot be stolen by this CLI or the Google worker.

The only additional gateway-role permission needed is `ecs:DescribeTasks`,
scoped to the gateway cluster's task ARNs (and optionally its `ecs:cluster`
condition). No `ecs:StopTask`, service updates, queue purge, cancellation, broad
Redis deletion, or database writes are part of this tool. Recovery releases only
the proven stopped owner's lock; request status and new explicit retries remain
separate operations.

## Data granularity and fetch modes

The Health API exposes the same underlying data through three different operations. Open Wearables picks one per the `DEFAULT_DATA_GRANULARITY` setting, and — at the finest granularity — the `GOOGLE_USE_RECONCILE` flag.

| Granularity | Operation | Resolution | Cross-source | Device attribution |
|-------------|-----------|------------|--------------|--------------------|
| `raw` + `GOOGLE_USE_RECONCILE=true` **(default)** | `dataPoints:reconcile` | native | **merged & deduplicated** | none |
| `raw` + `GOOGLE_USE_RECONCILE=false` | `dataPoints` (list) | native | raw, per-source | **per-device** |
| `hourly` / `daily` | `dataPoints:rollUp` | windowed | reconciled | none |

<Info>
`GOOGLE_USE_RECONCILE` only takes effect at `raw` granularity. Except for energy,
`hourly`/`daily` use windowed `rollUp` aggregates regardless of the flag. Energy v2
uses native reconcile intervals for `active-energy-burned`. For `total-calories`,
the live API rejects list with `UNSUPPORTED_DATA_TYPE_ACTION` and allows only
`rollup,dailyRollup`, despite the calories guide's list example. Totals therefore
use hourly rollups in chunks of at most 14 days by default, with unknown observed
coverage. An explicit `GOOGLE_ENERGY_CALENDAR_TIMEZONE` instead enables the
timezone-bound calendar-total mode described below.
Requests align to UTC hour boundaries (the current hour stops at now), so repeated
pulls update the same keys instead of accumulating sliding, overlapping windows.
Energy has merged source attribution rather than per-device attribution.
</Info>

### Reconcile vs. list — why it matters

A user commonly has the **same activity reported by multiple sources** (e.g. the phone's pedometer *and* the Fitbit app both counting steps). The two modes handle that overlap differently:

- **`reconcile` (default)** returns **one merged stream**, deduplicated across all sources at the interval level — exactly what the native Google Health / Fitbit app displays. There is no single device behind a merged value, so reconciled points carry **no device attribution** (`device_model` is empty).
- **`list`** returns the **raw per-source points**, each tagged with its originating device. This preserves device attribution but stores overlapping sources separately; Open Wearables then **deduplicates on read** by source priority (it does *not* sum them).

A concrete example — steps for one day for a user tracked by both their phone (Health Connect) and Fitbit MobileTrack:

| | steps |
|---|---|
| Fitbit MobileTrack (list, one source) | 2506 |
| Phone / Health Connect (list, one source) | 1919 |
| **`reconcile` (merged)** | **2560** |
| What the native health app shows | **2560** |

Reconcile (2560) matches the app exactly — it keeps intervals that *either* source captured while removing the overlap. Read-time dedup of the list data would instead pick a single source (1919), which is why **reconcile is the default**: it produces app-accurate totals.

<Note>
Choose `list` (`GOOGLE_USE_RECONCILE=false`) only when you specifically need per-device attribution (e.g. to know which watch recorded a reading). For app-matching totals, keep the default.
</Note>

## Daily energy contract (version 2)

`GET /api/v1/users/{user_id}/summaries/activity` accepts the optional **`timezone`**
query parameter, an IANA name such as `Asia/Bangkok`. Supply the same timezone on
every page of a cursor-paginated request. `start_date` is inclusive and `end_date`
exclusive; use civil date strings for local-day requests. Timezone-aware timestamp
bounds are converted to dates in the selected zone; date-only/naive bounds are
already civil dates. The timezone controls
live activity buckets, including energy intervals, steps, HR minutes, and workout
end dates. Omitting it retains stored offsets where available; Google energy with
neither an offset nor a selected timezone uses UTC buckets with **unknown**
coverage, not a claim about the user's local day. An invalid timezone returns 422.
Archived non-energy daily buckets retain their original dates because their
original intervals have already been discarded.

The existing nullable fields `active_calories_kcal` and `total_calories_kcal`
remain. `basal_calories_kcal` is additive and nullable. The following metadata
object is additive on every activity summary:

```json
{
  "date": "2026-09-08",
  "active_calories_kcal": null,
  "total_calories_kcal": 194.512,
  "basal_calories_kcal": null,
  "energy_metadata": {
    "version": 2,
    "metrics": {
      "active_calories": {
        "estimated": false,
        "coverage": "unknown", "intervals": [],
        "timezone": "Asia/Bangkok", "as_of": null,
        "reason": "no_records", "source_type": null
      },
      "total_calories": {
        "estimated": false,
        "coverage": "unknown", "intervals": [],
        "timezone": "Asia/Bangkok", "as_of": null,
        "reason": "intervals_unavailable", "source_type": "legacy_google_total"
      },
      "basal_calories": {
        "estimated": false,
        "coverage": "unknown", "intervals": [],
        "timezone": "Asia/Bangkok", "as_of": null,
        "reason": "no_records", "source_type": null
      }
    }
  }
}
```

This is the energy portion of a summary, not the entire paginated response.
Every metric metadata entry has:

| Field | Meaning |
|-------|---------|
| `coverage` | `complete`, `partial`, or `unknown` |
| `estimated` | Boolean, default false. True whenever any contributing interval is proportionally allocated, independently of coverage or reason |
| `intervals` | Union of observed native coverage as `{start, end}` ISO timestamp pairs, clipped to the selected local day; not fabricated rollup windows |
| `timezone` | Selected IANA timezone or null when only a fixed provider offset/unknown zone is available |
| `as_of` | Latest ingestion timestamp for the observations, or null for historical rows without provenance |
| `reason` | Optional explanation of gaps, missing evidence, overlap, or proportional allocation |
| `source_type` | Provider data type or explicit legacy provenance |
| `aggregation` | Optional calendar-total provenance, distinct from observed interval coverage; null without a qualifying calendar rollup |

Metadata coalesces adjacent and overlapping observed intervals, preserving every
gap. A continuous day of minute-level samples therefore returns one interval,
not 1,440 entries. No raw sample lists are embedded in activity summaries.
Compaction does not upgrade partial or unknown coverage to complete.
Interval resolution uses a sorted boundary sweep and priority heap, with
boundary counts for overlap detection: O(n log n) time and O(n) space per
metric/day. Expired entries may remain buried in the heap, but are never
rescanned at each boundary.
Consumers must label values as estimated when `estimated=true`, even when
`reason="interval_coverage_unavailable"` or another higher-priority reason hides
the proportional-allocation explanation. For compatibility, also recognize
`reason="proportional_interval_allocation"` as estimated.

`complete` requires actual native intervals whose union exactly spans the
matching local day, without uncertain overlap or proportional allocation.
DST days can span 23 or 25 hours. A historical date, successful pagination,
a plausible total, or a rollup's start/end window **never** proves complete
on-wrist coverage. Provider start and end offsets are retained. Intervals extending beyond their ingestion time
cannot be complete. Fixed offsets are retained; offset changes within a day
without an explicit IANA timezone leave coverage unknown.

An interval crossing midnight is split proportionally by elapsed time. The
result is **partial**, with `reason="proportional_interval_allocation"`, not a
measured calorie value for either subinterval. Overlapping intervals are never
added twice: finer intervals take precedence, then newer ingestion revisions.
Overlaps remain partial. A partial daily row cannot suppress valid finer data.
Native upserts use the existing `(data_source_id, series_type_definition_id,
recorded_at)` identity and update interval/provenance along with the value.

Google's `active-energy-burned` is stored as `active_energy` (ID 89), separately
from `total_energy` (ID 90). Active energy includes movement outside workouts.
Workout gross calories remain separate and are not added to daily active energy.
There is no Google basal/BMR endpoint and no app-BMR subtraction in this gateway.
Missing data is null; explicit zero is retained, including zero total rollups.
For applicable native list types (steps and distance), a valid interval with
an omitted value field is a true zero, per Google's
[data-presence documentation](https://developers.google.com/health/data-presence-and-true-zeros).
That rule is not applied to active energy, which is not listed as supporting it.

Legacy Google `energy` (ID 81) is **never** trusted as active. Known
`google_health_api` legacy rows can contribute only a total with unknown coverage
and no invented interval ends. Once corrected total rollups exist for that day,
legacy window sums are not added to them because their overlap is unknown.
Lossy archived Google energy buckets are excluded, not misrepresented as active
or re-dated without interval evidence. Other providers' `energy` semantics
are unchanged; their metadata remains unknown unless interval evidence exists.
For legacy providers, total is computed only when both active and basal exist;
missing basal is never silently converted to zero.

### Calendar totals without claiming complete sensor coverage

Set `GOOGLE_ENERGY_CALENDAR_TIMEZONE=Asia/Bangkok` in the gateway worker's
configuration to fetch Google totals over that timezone's calendar days. Leave
it unset to retain canonical UTC-hour totals. Invalid IANA names fail
configuration validation. Other providers and Google active-energy ingestion
are unchanged. The summary consumer must still request `timezone=Asia/Bangkok`.

Google's [dailyRollUp reference](https://developers.google.com/health/reference/rest/v4/users.dataTypes.dataPoints/dailyRollUp)
and [discovery schema](https://health.googleapis.com/$discovery/rest?version=v4)
define `range.start/end` as `CivilDateTime` objects containing `date` and optional
`time`. **Neither request nor response supports a timezone or UTC offset.**
Do not attach a requested IANA timezone to a civil response as if Google verified
it. Instead, calendar-total mode calls `dataPoints:rollUp` for `total-calories`,
using exact physical midnight boundaries in the configured timezone:

```json
{
  "range": {
    "startTime": "2026-09-07T17:00:00Z",
    "endTime": "2026-09-08T17:00:00Z"
  },
  "windowSize": "86400s",
  "pageSize": 1
}
```

This is September 8 in Bangkok. The default source family is `all-sources`,
as defined by Google. The gateway requires the returned physical start and end
to match the request exactly, and reads `totalCalories.kcalSum`. Missing values
remain missing; explicit zero remains zero. One request is made per local day,
with 23/25-hour windows on DST transitions. A past-day webhook naming just one
changed hour re-fetches the entire local day. Today's upper bound is fetch time,
rounded down to a whole second, not the following midnight.

An eligible completed-day total exposes this **additional** object under
`energy_metadata.metrics.total_calories.aggregation`:

```json
{
  "kind": "calendar_day",
  "source": "google_total_calories_rollup",
  "data_source_family": "all-sources",
  "date": "2026-09-08",
  "timezone": "Asia/Bangkok",
  "interval": {
    "start": "2026-09-07T17:00:00Z",
    "end": "2026-09-08T17:00:00Z"
  },
  "as_of": "2026-09-09T00:00:00Z",
  "complete": true
}
```

The metric itself still has `coverage="unknown"`, `intervals=[]`,
`estimated=false`, and `reason="calendar_aggregation_not_wear_coverage"`.
`aggregation.complete` means Google returned a total for the exact entire
calendar aggregation window after it ended. It **does not** assert continuous
wear, physiological measurement completeness, or that late provider updates
can no longer revise the total. A past date or successful pagination alone
never creates this provenance.

The summary selects this full-day total instead of adding contained hourly
windows. It requires ingestion version 2, matching persisted IANA provenance,
exact selected-day boundaries, and an ingestion timestamp at or after the
window end, no older than other available readings. A partial/current-day
calendar response, an unmatched requested timezone, unversioned rows, and
legacy totals do not qualify and have `aggregation=null`. Partial aggregates
still cannot suppress finer intervals; proportional combinations retain
`estimated=true`.

Consumers estimating historical active calories as total minus their own BMR
must independently validate the aggregation source, date, timezone, exact
local-day interval, fetch timestamp, and `complete` flag. That subtraction is
an **estimate**, not Google-reported active calories. Never subtract a full-day
BMR from a partial/current-day total. The gateway does not do the subtraction
or infer basal calories.

No migration beyond energy-v2 `e2a947bc103d` is required: the IANA binding is
persisted in `source_type="total-calories:calendar-rollup:Asia/Bangkok"` alongside
the existing physical interval and ingestion timestamp. Calendar totals use
the same `total_energy` series and canonical midnight upsert key; repeat pulls
revise that row. They are not added to older hourly rows. Enable the setting
and reload worker code only after existing owned pulls drain, then arrange one
explicit bounded re-fetch. Merely changing configuration does not repair
already-stored summaries.

Example read, using a key supplied through the process environment:

```bash
curl --fail-with-body --get \
  "http://localhost:8000/api/v1/users/00000000-0000-0000-0000-000000000001/summaries/activity" \
  -H "X-Open-Wearables-API-Key: $OPEN_WEARABLES_API_KEY" \
  --data-urlencode "start_date=2026-09-07" \
  --data-urlencode "end_date=2026-09-09" \
  --data-urlencode "timezone=Asia/Bangkok"
```

An empty `data` array means no eligible summary, not zero energy. Authorization
and existing pagination behavior are unchanged; no new endpoint or rate limit
is introduced.

### Migration and coordinated rollout

Apply Alembic revision **`e2a947bc103d`** before starting the corrected API and
workers. It adds nullable interval/provenance columns and registers IDs 89/90.
It does not relabel or delete historical rows. Downgrade deliberately fails while
rows reference the new series IDs, rather than discarding corrected data.

Google energy is excluded from lossy daily archival so interval evidence survives.
This increases retained live-row storage when archival is enabled; the separately
configured explicit deletion policy is unchanged. Already archived intervals
cannot be reconstructed from daily sums.

Google historical and live pulls retain mutual exclusion. Lock contention
schedules at most five retries (60, 120, 240, 480, and 900 seconds), reports
deferral/failure explicitly, and never advances the live cursor for a skipped
pull. Failed energy fetches also retain the cursor and expose the failed data
type rather than reporting empty success. Repeated consent errors require
operator/user action, not invented zeros. Initial connections still require an
explicit historical range to retrieve earlier history.

An explicit Google `sync/historical?days=8` queues a new rolling eight-day pull
and re-fetches existing intervals for upsert. It does **not** cancel or supersede
an automatic 90-day pull already queued by OAuth. The OAuth grace-period flag
is a compatibility setting, not a cancellable timer: integrations that explicitly
request history must separately configure `HISTORICAL_SYNC_ON_CONNECT=false`.
Already running work retains its original range. Do not restart a worker with
active work solely to load this code; coordinate worker reload and the final
bounded sync after active work drains.

The manually invoked repair module
`scripts/data_migrations/repair_google_energy.py` defaults to a read-only scoped
report. Its module docstring documents authorization scope, explicit apply,
before-state snapshots, conflict handling, and limitations. It is **not** an
automatic startup migration or a provider re-fetch. Coordinate native historical
sync and downstream cache/energy-field invalidation separately after reviewing
the report. Deployment, actual account consent/capability verification, and any
live repair require separate approval.

## What you need by the end

- A **Google Cloud project** with the Health API enabled
- **OAuth client credentials** (Client ID + Secret) with the Google Health scopes
- **Redirect URI** registered in your OAuth client
- *(Webhooks only)* A **service account** for project-level subscriber registration

## Prerequisites

- A [Google Cloud](https://console.cloud.google.com) project
- Access to the Google Health API for that project (`gcloud services enable health.googleapis.com`)

## Application walkthrough

<Steps>
  <Step title="Enable the Health API and create an OAuth client">
    In the [Google Cloud Console](https://console.cloud.google.com), select your project and enable the Health API:

    ```bash
    gcloud config set project YOUR_PROJECT_ID
    gcloud services enable health.googleapis.com
    ```

    Then create an **OAuth 2.0 Client ID** (Web application) under **APIs & Services → Credentials**, and add your server-side callback as an **Authorized redirect URI**:

    - Local dev: `http://localhost:8000/api/v1/oauth/google/callback`

    <Warning>
    Store the Client Secret securely — Google shows it once.
    </Warning>
  </Step>

  <Step title="Configure credentials in Open Wearables">
    Add the following to your `.env` file:

```bash
#--- Google ---#
GOOGLE_CLIENT_ID=your-google-client-id
GOOGLE_CLIENT_SECRET=your-google-client-secret
GOOGLE_DEFAULT_SCOPE=openid email https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly https://www.googleapis.com/auth/googlehealth.nutrition.readonly https://www.googleapis.com/auth/googlehealth.sleep.readonly https://www.googleapis.com/auth/googlehealth.settings.readonly
# Fetch mode for raw-granularity 24/7 data (see "Data granularity and fetch modes")
GOOGLE_USE_RECONCILE=true
```

    **Configuration details:**

    | Variable | Description | Default |
    |----------|-------------|---------|
    | `GOOGLE_CLIENT_ID` | OAuth Client ID | — |
    | `GOOGLE_CLIENT_SECRET` | OAuth Client Secret | — |
    | `GOOGLE_DEFAULT_SCOPE` | Space-separated Health API scopes to request | (full read-only set) |
    | `GOOGLE_USE_RECONCILE` | `true` = reconcile (merged, app-accurate, no device attribution); `false` = list (per-device). Only applies at `raw` granularity. | `true` |
    | `GOOGLE_ENERGY_CALENDAR_TIMEZONE` | Optional IANA timezone for exact local-day Google total-calorie rollups. Does not establish sensor wear coverage. | unset (hourly totals) |
    | `DEFAULT_DATA_GRANULARITY` | `raw` \| `hourly` \| `daily` — see the [fetch modes](#data-granularity-and-fetch-modes) table | `raw` |

    <Note>
    The redirect URI is derived from `API_BASE_URL` — it must match the Authorized redirect URI on your OAuth client (`{API_BASE_URL}/api/v1/oauth/google/callback`).
    </Note>
  </Step>

  <Step title="Connect a user via OAuth">
    With credentials configured and your instance running, initiate the OAuth flow.

    <Tip>
    **Using the Open Wearables frontend?** You don't need any of the curls below — open the connect view and click **Connect** on Google Health. The frontend runs this whole authorize → consent → callback → verify flow for you. The steps below are for integrating directly against the API.
    </Tip>

    **1. Get the authorization URL:**

    ```bash
    curl -X GET "http://localhost:8000/api/v1/oauth/google/authorize?user_id={user_id}&redirect_uri=http://localhost:3000/users/{user_id}" \
      -H "X-Open-Wearables-API-Key: YOUR_API_KEY"
    ```

    **2. Redirect the user** to the returned `authorization_url`. They log in to Google and grant consent.

    **3. Google redirects back** to `{API_BASE_URL}/api/v1/oauth/google/callback`; Open Wearables exchanges the code for tokens and stores the connection. It also resolves the user's stable `healthUserId` (via the Health API identity endpoint) as the connection's provider user id — this is what inbound webhooks are matched against.

    **4. Verify the connection:**

    ```bash
    curl -X GET "http://localhost:8000/api/v1/users/{user_id}/connections" \
      -H "X-Open-Wearables-API-Key: YOUR_API_KEY"
    ```

    You should see a connection with `"provider": "google"` and `"status": "active"`.
  </Step>

  <Step title="Sync data">
    An initial sync runs automatically after a successful OAuth connection. To trigger one manually:

    ```bash
    curl -X POST "http://localhost:8000/api/v1/providers/google/users/{user_id}/sync" \
      -H "X-Open-Wearables-API-Key: YOUR_API_KEY"
    ```
  </Step>

  <Step title="Verify the integration">
    Fetch a synced 24/7 series (e.g. steps):

    ```bash
    curl -X GET "http://localhost:8000/api/v1/users/{user_id}/timeseries/steps?start_date=2026-01-01T00:00:00Z&end_date=2026-02-01T00:00:00Z" \
      -H "X-Open-Wearables-API-Key: YOUR_API_KEY"
    ```

    If data is returned, your Google Health API integration is working end-to-end.
  </Step>
</Steps>

## Webhooks

Google Health webhooks are **notify-only**: each notification names the changed `dataType`, `operation` (`UPSERT`/`DELETE`), and the physical-time `intervals` that changed — but carries no data. Open Wearables verifies the request, then fetches the changed data over REST for those intervals.

Two distinct secrets are involved:

- **`GOOGLE_WEBHOOK_SECRET`** — a bearer token you register with Google that it echoes back in the `Authorization` header of every notification, so Open Wearables can verify the ping is genuine. Defaults to `SECRET_KEY` if unset.
- **Service-account credentials** — used only to *register* the subscriber (a project-level admin call). Not involved in receiving notifications.

<Info>
Receiving and processing webhooks needs only `GOOGLE_WEBHOOK_SECRET`. The service account is required only to register the subscriber programmatically — you can also register it manually via `gcloud`/the API console.
</Info>

### Webhook subscriber registration

Subscribers live at the **project** level (`POST /v4/projects/{project}/subscribers`), so registration authenticates as the project via a **service account**, not a user's OAuth token.

<Warning>
`gcloud` commands need the project **ID** (e.g. `open-wearables-prod`). The `GOOGLE_PROJECT_ID` env var, however, needs the project **number** (e.g. `123456789012`) — the subscriber API requires the number in its path.
</Warning>

<Steps>
  <Step title="Create a service account">
    ```bash
    gcloud iam service-accounts create health-webhooks \
      --project=YOUR_PROJECT_ID \
      --display-name="Health API webhook subscriber registration"

    # Grant a role that can manage Health API subscribers (narrow this to the
    # dedicated Health API role once confirmed; roles/editor works but is broad):
    gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
      --member="serviceAccount:health-webhooks@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
      --role="roles/editor"
    ```
  </Step>

  <Step title="Provide the credentials">
    Either mount a JSON key and point to it, or rely on Application Default Credentials (ADC) if running on GCP:

    ```bash
    gcloud iam service-accounts keys create ./config/health-webhooks-key.json \
      --project=YOUR_PROJECT_ID \
      --iam-account=health-webhooks@YOUR_PROJECT_ID.iam.gserviceaccount.com
    ```

    Add to `.env`:

    ```bash
    GOOGLE_PROJECT_ID=your-project-number   # the numeric project NUMBER, not the ID
    GOOGLE_SERVICE_ACCOUNT_FILE=config/health-webhooks-key.json   # unset = use ADC
    # GOOGLE_WEBHOOK_SECRET=your-token   # optional; defaults to SECRET_KEY
    ```

    <Warning>
    Subscriber registration runs in the **Celery worker**, not the backend/API service. The key file (or credentials) and the `GOOGLE_*` env vars must be present on the **worker** service — a key mounted only into the backend container won't be seen.
    </Warning>

    <Warning>
    A JSON key never expires until deleted — prefer ADC / Workload Identity in production, and keep key files out of version control.
    </Warning>
  </Step>

  <Step title="Register the subscriber">
    Switching the provider's live sync mode to `webhook` registers the subscriber automatically. Google then performs an endpoint-verification handshake (`POST {"type":"verification"}`) against `{API_BASE_URL}/api/v1/providers/google/webhooks`, which must return `2xx` when authenticated. Once verified, notifications begin flowing.
  </Step>
</Steps>

| Variable | Description | Default |
|----------|-------------|---------|
| `GOOGLE_PROJECT_ID` | GCP project **number** (not ID) that owns the subscriber. Get it with `gcloud projects describe YOUR_PROJECT_ID --format='value(projectNumber)'`. | — |
| `GOOGLE_SERVICE_ACCOUNT_FILE` | Path to the SA JSON key; unset uses ADC | — |
| `GOOGLE_WEBHOOK_SECRET` | Bearer secret Google echoes on notifications | `SECRET_KEY` |

### Managing subscribers without app credentials (gcloud / console)

If you'd rather not give the app a service account, create and manage the subscriber
yourself and leave `GOOGLE_SERVICE_ACCOUNT_FILE`/`GOOGLE_PROJECT_ID` unset. The app then
needs only `GOOGLE_WEBHOOK_SECRET` to verify inbound notifications — it never calls the
project-level subscriber API.

<Info>
In this mode the in-app `.../webhooks/subscriptions` management endpoints (list / register /
update / delete) won't work — they require project credentials. Use the commands below instead.
</Info>

<Warning>
The `endpointAuthorization.secret` you set here **must** equal `"Bearer "` + the app's
`GOOGLE_WEBHOOK_SECRET` (which defaults to `SECRET_KEY`). If they don't match, every
notification fails signature verification and Open Wearables returns 401.
</Warning>

All calls authenticate with your own gcloud identity, which must hold the Health API
subscriber role on the project. You can also run these from the Cloud Console API Explorer,
but the CLI steps below are easier to copy end-to-end. Use the same `subscriberId`
(`open-wearables`) the app uses, so it stays interchangeable.

```bash
TOKEN=$(gcloud auth print-access-token)
PROJECT=your-project-number   # numeric project number

# Create
curl -X POST \
  "https://health.googleapis.com/v4/projects/${PROJECT}/subscribers?subscriberId=open-wearables" \
  -H "Authorization: Bearer ${TOKEN}" -H "Content-Type: application/json" \
  -d '{
    "endpointUri": "https://YOUR_API_BASE_URL/api/v1/providers/google/webhooks",
    "subscriberConfigs": [
      {"dataTypes": ["steps", "distance", "heart-rate", "sleep", "exercise"], "subscriptionCreatePolicy": "AUTOMATIC"}
    ],
    "endpointAuthorization": {"secret": "Bearer YOUR_GOOGLE_WEBHOOK_SECRET"}
  }'

# List
curl "https://health.googleapis.com/v4/projects/${PROJECT}/subscribers" \
  -H "Authorization: Bearer ${TOKEN}"

# Update the callback URL (endpoint re-verification runs again)
curl -X PATCH \
  "https://health.googleapis.com/v4/projects/${PROJECT}/subscribers/open-wearables?updateMask=endpointUri" \
  -H "Authorization: Bearer ${TOKEN}" -H "Content-Type: application/json" \
  -d '{"endpointUri": "https://NEW_URL/api/v1/providers/google/webhooks"}'

# Delete
curl -X DELETE \
  "https://health.googleapis.com/v4/projects/${PROJECT}/subscribers/open-wearables" \
  -H "Authorization: Bearer ${TOKEN}"
```

<Note>
`dataTypes` above is an abbreviated example — use the set the app supports for webhooks
(steps, distance, hydration-log, heart-rate, run-vo2-max, daily-resting-heart-rate,
heart-rate-variability, weight, body-fat, blood-glucose, daily-respiratory-rate, sleep,
exercise). Registering a data type the app doesn't handle just means its notifications are ignored.
</Note>
